# Техническое задание
## Анализатор DNS трафика для выявления признаков туннелирования

Учебный проект по дисциплине «Алгоритмизация и программирование»

Наименование программы: DNS Security Analyzer.
Версия технического задания: 2.0 от 14 ноября 2026 года.
Состав исполнителей: Кирилл, Стёпа, Илья, Миша.

## 1 Общие положения

Настоящее техническое задание устанавливает назначение, состав функций, ограничения, распределение обязанностей и порядок приёмки программы DNS Security Analyzer. Разрабатывается локальная консольная программа для анализа записанного DNS-трафика и выявления признаков передачи произвольных данных в DNS-запросах.

Основание разработки: выполнение командного учебного проекта по дисциплине «Алгоритмизация и программирование» и уточнение предметной области по замечаниям преподавателя. Настоящая редакция заменяет первоначальную концепцию анализатора общей DNS-статистики.

## 2 Назначение и актуальность

DNS-туннелирование представляет собой передачу данных иных протоколов или приложений внутри DNS-запросов и ответов. Данная техника может применяться для скрытого управления программами и вывода данных из сети. Unit 42 описывает реальные кампании DNS-туннелирования [1]; FIRST указывает на необходимость анализа совокупности признаков и на сложность отделения туннелей от обычного DNS-трафика [2].

Назначение программы: выделение подозрительных сочетаний «клиент — базовый домен — временной интервал», представление оснований срабатывания и сопоставление результатов правил с результатами нейросетевого классификатора.

Пользователь программы — участник учебного исследования либо специалист, выполняющий первичный анализ записи трафика. Результат является основанием для последующей проверки. Программа не устанавливает факт заражения, не подтверждает содержимое утечки и не предотвращает передачу данных.

## 3 Границы разработки

Обязательный вход: файл PCAP с нефрагментированными IPv4-пакетами, содержащими обычные DNS-сообщения по UDP с портом отправителя либо получателя 53. Поддерживаются запросы и ответы с доступным первым DNS-вопросом. Основной анализ туннелирования выполняется по запросам; ответы используются для общей статистики.

В состав разработки не входят перехват и блокировка трафика, расшифрование DoH и DoT, DNS по TCP, IPv6, восстановление IP-фрагментов, разработка собственного бинарного парсера PCAP, извлечение исходных переданных файлов и веб-интерфейс. DGA и фишинговые домены не являются самостоятельными целями данной редакции.

## 4 Требования к обработке данных

ФР-01. Программа должна принимать путь к PCAP, путь к настройкам, режим анализа и префикс выходных файлов. Должны поддерживаться режимы rules, model и hybrid. Правила должны работать без файла модели; режимы model и hybrid требуют подготовленной модели.

ФР-02. Для каждого пригодного DNS-пакета должны извлекаться номер пакета, время захвата, адрес клиента, адрес DNS-сервера, имя, тип вопроса, признак ответа и код ответа. Для запроса клиентом считается отправитель, для ответа — получатель. Анализ предполагает запись со стороны клиентов до объединения их трафика трансляцией адресов; при иной точке захвата адрес обозначает только наблюдаемого отправителя.

ФР-03. Имена должны приводиться к нижнему регистру без конечной точки. Пригодными считаются непустые ASCII-имена с буквами a–z, цифрами, дефисом, подчёркиванием и разделяющими точками. Пустые метки, корневой вопрос и неподдерживаемые имена пропускаются с отдельным счётчиком. Имена в представлении Punycode допускаются как ASCII. При нескольких вопросах учитывается только первый.

ФР-04. Для имени должны определяться базовый домен и поддомен. Базовый домен состоит из публичного суффикса и ближайшей метки слева. Например, для a.b.example.co.uk базовый домен — example.co.uk, поддомен — a.b. Следует использовать локальную фиксированную копию Public Suffix List с учётом её частного раздела. Для неизвестного суффикса применяется правило последней метки; однокомпонентное имя считается базовым доменом без поддомена.

ФР-05. Запросы должны группироваться по паре «адрес клиента, базовый домен» независимо от использованного DNS-сервера. Для каждой группы формируются неперекрывающиеся окна длительностью 60 и 300 секунд. При длительности W начало окна равно floor(t / W) × W; левая граница включается, правая исключается. Каждый запрос попадает в одно окно каждого масштаба. Пустые окна не создаются.

ФР-06. На каждом окне должны вычисляться признаки, перечисленные в разделе 5. Окна менее чем с 10 запросами сохраняются со статусом «недостаточно данных» и не классифицируются. Длительности и минимальное число запросов должны задаваться настройками.

ФР-07. Должна рассчитываться общая статистика: число пригодных запросов и ответов, число уникальных полных имён в запросах, топ-10 имён, распределение запросов по типам, число ответов NXDOMAIN и число пропущенных пакетов по причинам. NXDOMAIN учитывается только по ответам с кодом 3. Сопоставление ответа с запросом для этого счётчика не требуется.

ФР-08. В результатах должны сохраняться ссылки на номера исходных пакетов. Повторно наблюдаемые пакеты учитываются как отдельные события. Удаление сетевых повторов в обязательный объём не входит.

## 5 Вычисляемые признаки

Для каждого запроса строка S образуется из поддомена удалением разделяющих точек. Длина, состав символов и энтропия рассчитываются для S. При отсутствии поддомена S является пустой строкой. Во всех средних значениях учитываются все N запросов окна, в том числе запросы с пустым S.

| Признак | Определение |
| --- | --- |
| Число запросов | N — число запросов клиента к базовому домену в окне |
| Частота запросов | N / W, запросов в секунду, где W — полная длительность окна |
| Средняя длина поддомена | Сумма длин S, делённая на N |
| Максимальная длина поддомена | Наибольшая длина S в окне |
| Средняя энтропия | Среднее значение H(S) по запросам; для пустой строки H = 0 |
| Доля цифр | Число цифр во всех S / суммарная длина всех S; при нулевой длине — 0 |
| Доля уникальных поддоменов | Число различных нормализованных поддоменов с сохранением внутренних точек / N; пустой поддомен является одним значением |
| Доля запросов TXT | Число запросов типа TXT / N |
| Объём строк поддоменов | Сумма длин S в ASCII-байтах с учётом повторов |
| Средний интервал | Среднее расстояние по времени между соседними запросами после сортировки; при N = 1 — 0 |

Энтропия рассчитывается по формуле Шеннона: H(S) = −Σ p(c) × log₂ p(c), где p(c) — доля символа c в строке S. Значение характеризует распределение символов и самостоятельно не подтверждает передачу данных.

Объём строк поддоменов характеризует только наблюдаемые имена. Он не должен обозначаться как объём украденных данных или размер восстановленного файла.

## 6 Обнаружение на основе правил

ФР-09. Для пригодного окна должны независимо проверяться пять условий. Начальная конфигурация приведена ниже. Во всех сравнениях применяется знак «больше или равно».

| Условие | Начальный порог |
| --- | --- |
| Средняя длина поддомена | 40 символов |
| Средняя энтропия | 3,5 бита на символ |
| Доля уникальных поддоменов | 0,80 |
| Частота запросов | 1 запрос в секунду |
| Доля запросов TXT | 0,30 |

Окно считается подозрительным по правилам при выполнении не менее двух условий. Все пороги и необходимое число условий задаются настройками. Для каждого сработавшего условия должны сохраняться название признака, измеренное значение и порог. Эти значения являются исходными параметрами разработки; окончательная конфигурация фиксируется до контрольного испытания и включается в комплект поставки.

## 7 Нейросетевой классификатор

ФР-10. Должен быть реализован бинарный классификатор окон на основе многослойного персептрона. Допускается применение MLPClassifier библиотеки scikit-learn. Вход классификатора — десять числовых признаков раздела 5 в фиксированном порядке. Адреса, имена доменов, метки класса и идентификаторы источников не должны передаваться в модель как признаки.

ФР-11. Обучение должно выполняться отдельной командой на размеченных данных. Требуется сохранить преобразование признаков, обученные параметры, порядок признаков, порог решения, случайное начальное состояние, версии зависимостей и описание обучающей выборки. При анализе PCAP обучение не выполняется. Работа должна быть возможна на центральном процессоре без видеокарты и внешнего сервиса.

ФР-12. Модель должна возвращать оценку класса «признаки туннелирования» в диапазоне от 0 до 1. Решение принимается при оценке не ниже установленного порога; исходный порог — 0,5. Оценка модели не должна представляться как доказанная вероятность атаки. Масштабирование и подбор параметров выполняются только по обучающей и валидационной частям.

ФР-13. Разделение данных должно выполняться по исходным сеансам записи до формирования окон. Окна двух масштабов и фрагменты одного сеанса не должны попадать в разные части. Домены туннелей контрольной части не должны встречаться в обучающей части. Дубликаты исходных записей должны исключаться. Происхождение, разметка и принадлежность к части набора фиксируются в реестре данных.

## 8 Совместное решение и отчёт

ФР-14. В режиме rules используется решение правил, в режиме model — решение модели. В режиме hybrid окно считается подозрительным, если сработал хотя бы один из методов. В отчёте должны отдельно сохраняться результаты обоих методов и итоговое решение. Отсутствие модели в режиме hybrid не должно приводить к незаметному переходу в другой режим.

ФР-15. Подозрительные окна одного клиента и базового домена, пересекающиеся либо соприкасающиеся во времени, должны объединяться в инцидент. Объединение выполняется транзитивно. В инцидент включаются границы периода, методы обнаружения, значения признаков по исходным окнам и до пяти примеров имён с номерами пакетов. Пакеты из пересекающихся окон при подсчёте запросов инцидента учитываются однократно по номеру пакета.

ФР-16. Должны формироваться краткий вывод в консоль и два файла: TXT для чтения человеком и JSON для повторной обработки. Отчёт должен содержать входной файл и его SHA-256, режим, настройки, версии программы и модели, общую статистику, инциденты, окна с недостаточными данными и ограничения анализа. При отсутствии срабатываний используется формулировка «Признаки туннелирования по выбранным методам не выявлены».

## 9 Требования к выполнению и ошибкам

НФ-01. Программа должна выполняться под Python 3.11 или более новой совместимой версией. Для итоговой поставки фиксируются точные версии зависимостей и фактически проверенные версия Python и операционная система. В обязательный объём входит проверка установки и запуска хотя бы на одной ОС из Windows, Linux или macOS.

НФ-02. После установки зависимостей и получения файлов модели и списка суффиксов анализ должен выполняться без доступа к сети. Запросы к доменам из исследуемого PCAP не отправляются. PCAP открывается только для чтения; его содержимое не изменяется. Загрузка модели допускается только из подготовленного командой файла.

НФ-03. Необходимо обрабатывать отсутствие файла, отказ в доступе, пустой файл, повреждение PCAP, неверные настройки, несовместимую либо отсутствующую модель и ошибку записи отчёта. Пользователю выводятся причина и относящийся к ошибке путь или параметр без полного служебного стека. Подробный стек допускается в отдельном отладочном режиме.

НФ-04. Повреждение контейнера PCAP должно завершать обработку без выдачи успешного итогового отчёта. Отдельные неподдерживаемые либо некорректные пакеты в корректном контейнере должны пропускаться с указанием количества. Корректный PCAP без пригодных DNS-запросов должен давать результат «Нет данных для анализа», а не сообщение об отсутствии угроз.

НФ-05. Коды завершения: 0 — обработка завершена, в том числе без данных; 2 — ошибка аргументов, входа, настроек или модели; 3 — ошибка сохранения результата. Наличие подозрений не является ошибкой выполнения. Имена выходных файлов формируются из префикса; существующие файлы заменяются только при явном параметре --overwrite.

НФ-06. При одинаковых входных данных, настройках и модели числовые результаты и состав инцидентов должны совпадать. Время формирования отчёта может различаться. Необходимо приводить измеренные время обработки и максимальный объём памяти на контрольном файле с указанием размера файла и характеристик компьютера; гарантии для произвольного оборудования не устанавливаются.

## 10 Состав поставки

В состав результата входят исходный код; файл зависимостей; настройки; фиксированная копия Public Suffix List с лицензией и контрольной суммой; модель и описание её обучения; реестр данных и инструкции их получения; демонстрационные PCAP либо воспроизводимые инструкции их формирования; автоматические проверки; руководство пользователя; отчёт об испытаниях с метриками и примерами ошибок.

Документация, параметры и команды должны соответствовать фактической версии программы. Утверждения о реализованных функциях допускаются после выполнения соответствующей проверки. Календарный график настоящим техническим заданием не устанавливается.

## 11 Распределение обязанностей

### Кирилл

Отвечает за модель общих данных, определение базовых доменов, группировку запросов, формирование окон, расчёт десяти признаков и общей статистики. Реализует командную строку, загрузку и проверку настроек, связывание модулей и обработку ошибок верхнего уровня. Ведёт технический контракт и проверяет согласованность итоговой поставки.

Результат: модуль признаков и статистики, точка входа, конфигурация, проверки формул и границ окон, инструкция запуска и работающий общий путь обработки.

### Стёпа

Отвечает за чтение PCAP, извлечение DNS-полей, нормализацию имён, фильтрацию неподдерживаемых пакетов и счётчики пропусков. Подготавливает демонстрационные записи, реестр происхождения и разметку по сеансам. Реализует средство формирования синтетических PCAP без отправки пакетов в сеть и подбирает независимый публичный пример для дополнительной проверки.

Результат: парсер, проверки DNS-пакетов и ошибок чтения, набор сценариев, реестр данных и команды воспроизведения примеров.

### Илья

Отвечает за пять условий обнаружения, применение порогов, объяснение решений, объединение окон в инциденты и устранение повторного подсчёта пакетов. Подготавливает граничные проверки детектора и совместно с Мишей сравнивает правила, модель и совместный режим. Проверяет, что контрольные данные не используются для настройки.

Результат: детектор правил, модуль инцидентов, проверки порогов и объединения, результаты базового метода и разбор ложных срабатываний.

### Миша

Отвечает за подготовку числовой выборки из размеченных сеансов, обучение персептрона, сохранение и загрузку модели, вычисление метрик и сопоставление методов. Реализует консольное представление, TXT- и JSON-отчёты, проверки их структуры и ошибок записи. Документирует параметры обучения и ограничения модели.

Результат: классификатор, команды обучения и оценки, файл модели с метаданными, формирование отчётов и отчёт об испытаниях.

Каждый участник разрабатывает проверки своей части и должен объяснить её алгоритмы, входные данные, выходные данные и ограничения. Изменения общего формата согласуются с владельцами зависимых модулей. Полные имена исполнителей при необходимости указываются в сопроводительных материалах учебной группы.

## 12 Контрольные испытания и приёмка

Приёмка проводится по итоговой версии программы, поставляемым настройкам и зафиксированной модели. Для каждой проверки сохраняются команда, контрольная сумма входа, ожидаемый и фактический результаты.

| Код | Проверка и требуемый результат |
| --- | --- |
| ПИ-01 | Запись с вручную проверенными DNS-сообщениями: число запросов и ответов, имена, клиенты, типы и NXDOMAIN совпадают с эталоном |
| ПИ-02 | Границы окон и разделение клиентов: событие на правой границе относится к следующему окну; разные клиенты не объединяются |
| ПИ-03 | Формулы признаков: значения на заданных строках и временах совпадают с эталоном с погрешностью не более 10⁻⁶ |
| ПИ-04 | Пороги правил: равенство порогу считается срабатыванием; одного условия недостаточно; 9 запросов дают статус недостаточных данных, 10 допускают классификацию |
| ПИ-05 | Интенсивная и малочастотная синтетические передачи: в режиме hybrid выявляется хотя бы один инцидент нужного клиента и домена в каждом сценарии; малочастотный сценарий содержит 10–30 запросов за 300 секунд |
| ПИ-06 | Пересекающиеся окна: создаётся единый инцидент с уникальными номерами пакетов и корректными границами |
| ПИ-07 | Модель и отчёты: сохранение и повторная загрузка не меняют решения; TXT и JSON согласованы; отсутствующая модель не подменяется правилами |
| ПИ-08 | Ошибки и отсутствие данных: соблюдаются НФ-03–НФ-05; файл без запросов не объявляется безопасным |

Контрольный набор для оценки качества должен содержать не менее 100 пригодных окон обычной активности и 100 пригодных окон туннелирования, полученных не менее чем из 10 независимых сеансов каждого класса. Обычная активность должна включать случаи с длинными именами и множеством уникальных поддоменов. Число окон каждого масштаба указывается отдельно.

Для rules, model и hybrid должны публиковаться TP, FP, TN, FN, precision = TP / (TP + FP), recall = TP / (TP + FN), F1 и FPR = FP / (FP + TN). TP — правильно выявленные окна туннелирования; FP — ошибочно отмеченные обычные окна. При нулевом знаменателе метрика отмечается как неопределённая.

Критерий качества совместного режима на зафиксированном контрольном наборе: recall не ниже 0,85 и FPR не выше 0,10. Это требование к результату разработки на указанном наборе, а не заявленная характеристика существующей программы. Превосходство нейросети над правилами заранее не предполагается. Дополнительно требуется проверка хотя бы на одном публичном PCAP туннелирования, не участвовавшем в настройке; её результат и ограничения отражаются отдельно без переноса показателей на все реальные сети.

Приёмка считается успешной при выполнении ПИ-01–ПИ-08, установленного критерия качества и наличии полного комплекта поставки. Источники данных и условия их использования подлежат указанию.

## 14 Термины

| Термин | Значение в настоящем задании |
| --- | --- |
| DNS | Система доменных имён; протокол запросов сведений о доменах |
| DNS-туннелирование | Передача произвольных данных в DNS-запросах и ответах |

| Инцидент | Объединённая группа соприкасающихся либо пересекающихся подозрительных окон одного клиента и домена |
| Персептрон | Нейросетевой классификатор числовых признаков с обучаемыми параметрами |
| Ложное срабатывание | Отнесение обычного окна к классу с признаками туннелирования |
