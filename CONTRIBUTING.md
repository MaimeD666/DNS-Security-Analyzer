# Работа над проектом

## Ветки и Pull Request

`main` — проверенная версия проекта. Первичное оформление пустого репозитория выполняет Кирилл; дальнейшие изменения проходят через PR с просмотром другим участником.

Перед новой задачей сохрани текущую работу, затем обнови `main` и создай ветку:

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/parser
```

Выбери ветку своей задачи: `feature/parser`, `feature/detector`, `feature/report`, `feature/statistics` или другое короткое понятное имя. Если ветка уже существует, переключись на неё через `git switch имя-ветки`.

После изменений:

```bash
git status
git diff
git add parser.py
git commit -m "Добавить чтение DNS-запросов из PCAP"
git push -u origin feature/parser
```

В `git add` укажи файлы своей задачи. Открой PR в `main` и заполни шаблон: что сделано, как проверить, что ещё не готово. Хотя бы один другой участник просматривает изменения до слияния. Эти правила пока описаны в документации; обязательное ревью техническими настройками GitHub не включено.

Не переписывай общую историю и не отправляй изменения в чужую ветку без договорённости. После слияния обнови локальную `main` перед следующей задачей.

## Общие интерфейсы

- Соблюдай [контракт](docs/contract.md): имена полей, типы и сигнатуры.
- Изменение общего формата сначала опиши в PR и обсуди с владельцами зависимых модулей.
- Для числа запросов используй только `is_response=False`; для NXDOMAIN — только ответы с `rcode=3`.
- Scapy отвечает за чтение и разбор пакетов. Алгоритмы статистики и обнаружения пишем сами.
- Держи код понятным: автор должен объяснить его на защите.

## Что добавлять в Git

Исходники, документацию, проверки и небольшие воспроизводимые демо-файлы. Не добавляй `.venv/`, `__pycache__/`, пароли, ключи и случайные дампы личного трафика.

В `samples/` допустимы только осознанно выбранные синтетические или публичные PCAP. Для каждого укажи происхождение, способ воспроизведения и ожидаемый результат в `samples/README.md`. При выборе публичного файла укажи источник и условия использования.

## Готовность задачи

- Изменения опубликованы на GitHub.
- Реализованная часть запускается, а инструкция проверки воспроизводима.
- Проверен ожидаемый результат и существенные граничные случаи.
- Документация соответствует коду; ограничения и незавершённая работа указаны явно.
- Автор понимает и может объяснить реализацию.
- PR просмотрен хотя бы одним другим участником перед merge.
