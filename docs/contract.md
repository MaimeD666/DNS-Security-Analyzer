# Контракт MVP — рабочая версия от 4 ноября 2026

Основание: разделы 2 и 5 [командного плана](../DNS_Security_Analyzer_Team_Plan.pdf). Контракт фиксирует исходную модель и пороги для разработки. Команде нужно подтвердить договорённости до **7 ноября**; факт общего согласования пока не зафиксирован.

## DNS-запись

`parse_pcap(path)` возвращает `list[dict]`. Для MVP читаем офлайн-PCAP и выделяем обычные DNS-пакеты по UDP/53.

| Поле | Тип | Значение |
| --- | --- | --- |
| `timestamp` | `float` | Время захвата пакета в секундах |
| `client_ip` | `str` | IP исходного клиента: адрес отправителя запроса или получателя ответа |
| `domain` | `str` | Запрошенное доменное имя в нижнем регистре, без конечной точки |
| `query_type` | `str` | Тип из DNS-вопроса, например `A`, `AAAA`, `MX`; неизвестный код — `TYPE<число>` |
| `rcode` | `int` или `None` | Код результата для ответа, `None` для запроса |
| `is_response` | `bool` | `False` для запроса, `True` для ответа |

Пример запроса и соответствующего отрицательного ответа:

```python
records = [
    {
        "timestamp": 0.0,
        "client_ip": "192.0.2.10",
        "domain": "missing.example",
        "query_type": "A",
        "rcode": None,
        "is_response": False,
    },
    {
        "timestamp": 0.1,
        "client_ip": "192.0.2.10",
        "domain": "missing.example",
        "query_type": "A",
        "rcode": 3,
        "is_response": True,
    },
]
```

Здесь **один запрос**, один уникальный запрошенный домен и **один NXDOMAIN**. Адрес DNS-сервера в `client_ip` не попадает.

Дополнительные договорённости этой рабочей версии:

- Одна запись соответствует одному DNS-пакету; в MVP используем первый DNS-вопрос, не создаём дополнительные записи по секции ответов.
- Имя `ExAmPlE.COM.` нормализуется в `example.com`; тип берётся из вопроса, а не из ресурсной записи ответа.
- Пакеты без DNS или без доступного DNS-вопроса пропускаются. Стёпа документирует ограничения обработки нестандартных пакетов в своём PR.
- Корректный PCAP без подходящих DNS-записей даёт `[]`; неверный путь и повреждённый PCAP не маскируются под отсутствие DNS. Конкретные исключения согласуем при реализации обработки ошибок.
- Если определение исходного клиента для ответов потребует упрощения, его нужно явно описать в контракте до 14 ноября.

## Интерфейсы модулей

| Функция | Вход | Результат |
| --- | --- | --- |
| `parse_pcap(path)` | Путь к `.pcap` | `list[dict]` DNS-записей |
| `calculate_stats(records)` | Список DNS-записей | `dict` со статистикой |
| `detect_anomalies(records, config)` | Записи и словарь порогов | `list[dict]` предупреждений |
| `show_report(stats, alerts)` | Статистика и предупреждения | Вывод в консоль, возвращает `None` |
| `save_report(stats, alerts, path)` | Статистика, предупреждения, путь | TXT-файл в UTF-8, возвращает `None` |

`main.py` связывает эти функции и загружает `config.json`. Сейчас файлы модулей — заготовки, эти функции ещё не реализованы.

## Статистика

Рабочий формат результата `calculate_stats`:

```python
{
    "total_queries": 1,
    "unique_domains": 1,
    "top_domains": [("missing.example", 1)],
    "query_types": {"A": 1},
    "nxdomain_count": 1,
}
```

`total_queries`, `unique_domains`, `top_domains` и `query_types` учитывают только запросы. `nxdomain_count` учитывает только ответы с `rcode=3`, независимо от наличия парного запроса в файле. Повторно наблюдаемые пакеты считаются отдельными фактами; дедупликация не входит в MVP.

`top_domains` — не более десяти пар `(домен, количество)`, по убыванию количества; при равенстве — по имени домена. Для `[]` счётчики равны нулю, `top_domains` — `[]`, `query_types` — `{}`.

## Настройки и правила

Единственный файл стартовых настроек — [config.json](../config.json):

| Ключ | Значение | Назначение |
| --- | --- | --- |
| `window_seconds` | `60` | Длина скользящего окна в секундах |
| `query_count_threshold` | `100` | Порог числа запросов клиента |
| `domain_length_threshold` | `80` | Порог длины нормализованного домена |
| `nxdomain_count_threshold` | `20` | Порог числа NXDOMAIN для клиента |

Все значения — положительные целые числа. Пороги сравниваем строго через **`>`**:

1. `query_rate`: более 100 запросов одного клиента за 60 секунд; ответы не учитываем.
2. `long_domain`: более 80 символов в нормализованном имени запроса, включая внутренние точки; ответы не учитываем.
3. `nxdomain_rate`: более 20 ответов с `rcode=3` для одного клиента за 60 секунд; запросы и ответы с другими кодами не учитываем.

Для частотных правил события группируем по клиенту и сортируем по времени. Окно для события в момент `t`: **`(t - 60, t]`**. Событие ровно на левой границе уже исключается. Это рабочая договорённость команды, уточняющая не заданную в PDF границу окна.

Примеры границ для проверки реализации:

| Случай | Ожидаемый результат |
| --- | --- |
| 100 запросов одного клиента внутри окна | Нет предупреждения о частоте |
| 101 запрос одного клиента внутри окна | Есть предупреждение о частоте |
| Длина домена 80 / 81 символ | Нет / есть предупреждение о длине |
| 20 / 21 ответ NXDOMAIN внутри окна | Нет / есть предупреждение NXDOMAIN |
| 60 запросов клиента A и 60 клиента B внутри окна | Нет предупреждения о частоте |
| События в `0.0` и `60.0` | Первое не входит в окно второго |

Это учебные эвристики. Срабатывание не означает заражение или атаку.

## Предупреждения

Рабочий формат одного элемента `alerts`:

```python
{
    "type": "query_rate",
    "client_ip": "192.0.2.10",
    "domain": None,
    "count": 101,
    "value": 101,
    "threshold": 100,
    "window_seconds": 60,
    "reason": "101 DNS-запрос от клиента за 60 секунд; порог — 100.",
}
```

`type` — одно из `query_rate`, `long_domain`, `nxdomain_rate`. `count` — число фактов; `value` — измеренная величина, которую сравниваем с порогом. Для частотных правил это одно и то же число, `domain=None`. Для `long_domain` указываем имя домена, `count=1`, `value=len(domain)`, `threshold=80`, `window_seconds=None`. `client_ip` и человекочитаемая `reason` обязательны.

При отсутствии аномалий возвращаем `[]`. Политику объединения повторных предупреждений Илья описывает в спецификации первой недели и согласует с Мишей до реализации отчёта. Его примеры на 8–10 записях можно проверять с уменьшенными порогами, явно указав тестовый `config`.
