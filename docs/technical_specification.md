# Техническое задание
## Анализатор DNS трафика для выявления признаков туннелирования

Учебный проект по дисциплине «Алгоритмизация и программирование»

Наименование программы: DNS Security Analyzer.
Версия документа: 2.1 от 14 ноября 2026 года.
Исполнители: Крутов Кирилл, Динда Степан, Кохан Илья, Минько Михаил.

## 1 Назначение разработки

Разработать локальную консольную программу для выявления признаков DNS-туннелирования в записанном сетевом трафике. Программа должна выделять подозрительные обращения, указывать адрес клиента, базовый домен и период активности, представлять основания обнаружения и сравнивать результаты правил с результатами нейросетевого классификатора.

Область применения — первичный анализ записи трафика при исследовании сетевого инцидента. Входными данными служит файл PCAP. Результат работы — сводная статистика и перечень подозрительных периодов с примерами исходных DNS-запросов.

## 2 Актуальность

DNS-туннелирование представляет собой передачу данных приложений внутри DNS-запросов и ответов. Такой канал может использоваться для скрытого обмена командами и вывода данных из сети. Unit 42 описывает реальные кампании применения этой техники [1]. FIRST отмечает, что обнаружение требует анализа совокупности признаков, поскольку отдельные необычные DNS-запросы встречаются и при штатной работе [2].

Задача проекта — обнаружение характерных сочетаний признаков имён и поведения клиента во времени. Наличие длинного имени или высокой частоты запросов рассматривается совместно с другими наблюдениями. Пользователь получает исходные значения признаков и ссылки на пакеты для дальнейшей проверки.

## 3 Объём разработки

Поддерживаемый вход: классический PCAP с кадрами Ethernet II и нефрагментированными IPv4-пакетами, содержащими DNS по UDP с портом отправителя либо получателя 53. При нескольких DNS-вопросах используется первый. Для обнаружения туннелирования анализируются запросы; ответы учитываются в общей статистике.

Обязательные функции: разбор пакетов, определение базовых доменов, временная группировка, расчёт десяти признаков, обнаружение по правилам, обучение и применение персептрона, объединение подозрительных окон, вывод в консоль и сохранение TXT и JSON, оценка качества на размеченной выборке.

За пределами разработки: перехват и блокировка трафика, PCAPNG, прочие канальные форматы, IPv6, DNS по TCP, DoH и DoT, восстановление IP-фрагментов, извлечение переданных файлов, веб-интерфейс. Программа выявляет признаки туннелирования; установление факта заражения и содержимого утечки выполняется при последующем расследовании.

## 4 Программные средства

Язык разработки — CPython 3.12, 64-разрядная версия. Базовая среда испытаний — Linux x86-64. Все компоненты выполняются на центральном процессоре. Установка зависимостей производится в виртуальное окружение одной командой из requirements.txt.

| Средство | Версия | Назначение |

| dpkt | 1.9.8 | Чтение PCAP и разбор Ethernet, IPv4, UDP, DNS |
| tldextract | 5.3.0 | Определение публичного суффикса и базового домена |
| NumPy | 2.3.5 | Числовые массивы признаков |
| scikit-learn | 1.8.0 | StandardScaler, Pipeline, MLPClassifier и метрики |
| SciPy | 1.17.0 | Численные процедуры обучения |
| joblib | 1.5.3 | Сохранение и загрузка обученного конвейера |

Для командной строки используются argparse и pathlib; для форматов данных — json и csv; для автоматических проверок — unittest. Дополнительные зависимости закрепляются в requirements.txt. Список суффиксов берётся из встроенного снимка tldextract указанной версии. Сетевое обновление списка отключается, частный раздел Public Suffix List включается.

## 5 Обработка исходных данных

ФР-01. Программа должна принимать путь к PCAP, путь к настройкам, режим rules, model или hybrid, путь к модели для model и hybrid и префикс выходных файлов. Команда --help должна выводить назначение параметров и пример запуска.

ФР-02. Для пригодного DNS-пакета извлекаются номер в исходном файле, время захвата, адрес клиента, адрес DNS-сервера, имя, тип вопроса, признак ответа и код ответа. Клиентом считается отправитель запроса либо получатель ответа. При анализе записи после трансляции адресов используется наблюдаемый адрес клиента.

ФР-03. Имена приводятся к нижнему регистру без конечной точки. Поддерживаются непустые ASCII-имена с буквами a–z, цифрами, дефисом, подчёркиванием и точками между непустыми метками; Punycode обрабатывается как ASCII. Корневые вопросы, некорректные имена и неподдерживаемые пакеты пропускаются с отдельными счётчиками.

ФР-04. Базовый домен определяется по Public Suffix List. Для a.b.example.co.uk базовый домен — example.co.uk, поддомен — a.b. При неизвестном суффиксе базовым доменом считаются последние две метки; однокомпонентное имя является базовым доменом без поддомена.

ФР-05. Запросы группируются по паре «клиент, базовый домен», независимо от DNS-сервера. Для каждой пары формируются окна 60 и 300 секунд. Начало окна W равно floor(t / W) × W. Левая граница включается, правая исключается. Пустые окна не создаются. При числе запросов менее 10 окно получает статус «недостаточно данных» и не классифицируется.

## 6 Признаки и правила обнаружения

Для каждого запроса строка S образуется из поддомена удалением точек. При отсутствии поддомена S является пустой строкой. Во всех средних учитываются все N запросов окна. Длительность W — полная длительность окна, в том числе неполного по фактически наблюдаемым событиям.

| Признак | Определение |
| --- | --- |
| Число запросов | N |
| Частота запросов | N / W, запросов в секунду |
| Средняя длина поддомена | Сумма длин S / N |
| Максимальная длина поддомена | Наибольшая длина S |
| Средняя энтропия | Среднее H(S); для пустой строки H = 0 |
| Доля цифр | Число цифр во всех S / суммарная длина S; при нулевой длине — 0 |
| Доля уникальных поддоменов | Число различных поддоменов с внутренними точками / N; пустой поддомен является одним значением |
| Доля запросов TXT | Число запросов TXT / N |
| Объём строк поддоменов | Сумма длин S в ASCII-байтах с учётом повторов |
| Средний интервал | Среднее расстояние между соседними запросами по времени; при N = 1 — 0 |

Энтропия вычисляется по формуле H(S) = −Σ p(c) × log₂ p(c), где p(c) — доля символа c в S. Объём строк характеризует наблюдаемые имена, а не размер переданного исходного файла.

ФР-06. Для каждого пригодного окна должны проверяться пять условий. Начальные значения задаются следующей таблицей; каждый порог сравнивается через «больше или равно».

| Условие | Порог |
| --- | --- |
| Средняя длина поддомена | 40 символов |
| Средняя энтропия | 3,5 бита на символ |
| Доля уникальных поддоменов | 0,80 |
| Частота запросов | 1 запрос в секунду |
| Доля запросов TXT | 0,30 |

Окно считается подозрительным по правилам при выполнении не менее двух условий. Для каждого срабатывания сохраняются название признака, его значение и порог. Длительности окон, минимальное число запросов, пороги и необходимое число условий должны изменяться через конфигурацию.

## 7 Обучение и применение модели

ФР-07. Нейросетевой классификатор реализуется как Pipeline из StandardScaler и MLPClassifier. Вход — десять признаков раздела 6 в указанном порядке. Два скрытых слоя содержат 16 и 8 нейронов; функция активации — ReLU; метод обучения — L-BFGS; max_iter = 1000; random_state = 42. Адреса, доменные имена, идентификаторы сеансов и метки класса в признаки не включаются.

ФР-08. Отдельная команда должна строить числовую выборку из размеченных сеансов, обучать модель, выбирать порог по валидационной части и сохранять конвейер с метаданными. Сохраняются порядок признаков, порог, параметры обучения, версии библиотек и идентификатор разбиения данных. Во время анализа PCAP используются сохранённые параметры без повторного обучения.

ФР-09. Для пригодного окна модель возвращает числовую оценку от 0 до 1. При оценке не ниже выбранного порога окно считается подозрительным. Первоначальный порог — 0,5. В отчёте значение обозначается как оценка классификатора.

ФР-10. Данные должны разделяться на обучающую, валидационную и контрольную части по исходным сеансам до формирования окон. Все фрагменты и оба масштаба одного сеанса остаются в одной части. Нормализатор обучается только на обучающей части; порог выбирается по валидационной. Контрольная часть используется для итоговой оценки. Дубликаты исходных записей исключаются.

В набор включаются обычная активность, обычная активность с длинными и уникальными поддоменами, интенсивная и малочастотная синтетическая передача. Требуется не менее 10 отдельных сеансов каждого класса. В контрольной части должны присутствовать не менее двух сеансов и 20 пригодных окон каждого класса. Домены синтетических туннелей контрольной части должны отличаться от доменов обучающей и валидационной частей. Происхождение и параметры генерации записей указываются в реестре данных.

## 8 Совместное решение

ФР-11. В режиме rules решение принимается по правилам, в режиме model — по модели. В hybrid достаточно срабатывания одного метода. В результатах должны отдельно сохраняться решение правил, оценка модели и итоговое решение. Для model и hybrid наличие совместимого файла модели обязательно.

ФР-12. Подозрительные окна одного клиента и базового домена, пересекающиеся либо соприкасающиеся во времени, должны объединяться в инцидент. Объединение выполняется транзитивно. При подсчёте числа запросов инцидента пакеты из пересекающихся окон учитываются однократно по исходному номеру. Инцидент содержит период, методы обнаружения, признаки исходных окон и до пяти примеров имён с номерами пакетов.

## 9 Представление результатов

ФР-13. Должна рассчитываться общая статистика: число запросов и ответов, число уникальных имён в запросах, топ-10 имён, распределение запросов по типам, число ответов NXDOMAIN и количество пропущенных пакетов по причинам. Для NXDOMAIN учитываются только ответы с кодом 3.

ФР-14. Результат выводится в консоль и сохраняется в файлы <префикс>.txt и <префикс>.json в UTF-8. Отчёт содержит входной файл и его SHA-256, режим и настройки, версии программы и модели, статистику, инциденты и количество окон с недостаточными данными. При отсутствии срабатываний выводится «Признаки туннелирования не выявлены». При отсутствии пригодных запросов выводится «Нет данных для анализа».

ФР-15. Отдельная команда оценки должна рассчитывать для rules, model и hybrid матрицу ошибок TP, FP, TN, FN, показатели precision, recall, F1 и FPR на одной и той же контрольной выборке. Для каждого режима сохраняются фактические значения и примеры ложных срабатываний и пропусков при их наличии.

## 10 Требования к надёжности и эксплуатации

НФ-01. После установки зависимостей анализ и обучение выполняются локально без доступа к сети. Программа не отправляет DNS-запросы и не изменяет исходный PCAP. Для работы не требуются видеокарта, внешний сервис или права администратора.

НФ-02. Должны обрабатываться неверный путь, отказ в доступе, пустой или повреждённый PCAP, неподдерживаемый канальный формат, неверные настройки, отсутствующая или несовместимая модель и ошибка записи результата. Пользователю выводится краткое сообщение с причиной и относящимся к ней путём либо параметром.

НФ-03. Ошибка структуры PCAP должна завершать обработку без выдачи успешного итогового отчёта. Некорректные отдельные пакеты в корректном контейнере пропускаются с учётом в статистике. Отсутствие срабатывания и отсутствие данных отображаются раздельно.

НФ-04. Коды завершения: 0 — обработка завершена; 2 — ошибка параметров, входа, настроек или модели; 3 — ошибка сохранения. Наличие подозрительного трафика не изменяет код успешного выполнения. Существующие отчёты заменяются только с параметром --overwrite.

НФ-05. Повторный анализ одного PCAP с одинаковыми настройками и моделью должен давать одинаковые числовые результаты и состав инцидентов. Время формирования отчёта может различаться. Модель сохраняется и загружается в одном закреплённом окружении проекта.

## 12 Порядок приёмки

Испытания проводятся на итоговой версии программы с комплектными настройками и моделью. Для каждой проверки сохраняются команда, входные данные, ожидаемый и фактический результаты.

| Код | Проверка и требуемый результат |
| --- | --- |
| ПИ-01 | Установка из requirements.txt и проверка окружения завершаются успешно; подтверждаются чтение и запись PCAP, локальный PSL, обучение и повторная загрузка персептрона |
| ПИ-02 | Поля DNS и общая статистика на небольшом контрольном PCAP совпадают с ручным эталоном |
| ПИ-03 | Событие на правой границе относится к следующему окну; разные клиенты и базовые домены не смешиваются |
| ПИ-04 | Десять признаков совпадают с ручными значениями с абсолютной погрешностью не более 10⁻⁶; равенство порогу считается срабатыванием |
| ПИ-05 | Одно условие не даёт срабатывания правил, два условия дают; 9 запросов означают недостаток данных, 10 допускают классификацию |
| ПИ-06 | На интенсивном и малочастотном учебных сценариях hybrid формирует инцидент для заданных клиента и домена; малочастотный сценарий содержит 10–30 запросов за 300 секунд |
| ПИ-07 | Пересекающиеся окна объединяются без повторного подсчёта пакетов; повторная загрузка модели сохраняет её решения |
| ПИ-08 | Консоль, TXT и JSON согласованы; ошибки, отсутствие данных, отсутствие модели и отказ перезаписи обрабатываются по разделу 10 |

Отчёт об оценке качества должен содержать состав трёх частей данных, число сеансов и пригодных окон каждого класса, параметры модели, выбранный порог и результаты трёх режимов на контрольной части. Для окон с известной меткой рассчитываются precision = TP / (TP + FP), recall = TP / (TP + FN), F1 = 2TP / (2TP + FP + FN), FPR = FP / (FP + TN). При нулевом знаменателе указывается отсутствие определённого значения.

Оценка выполняется на уровне окон. Показатели приводятся раздельно для масштабов 60 и 300 секунд и для их совокупности. Недостаточные и неоднозначно размеченные окна в метрики не включаются; их количество указывается отдельно. Сравнительный вывод должен опираться на фактические значения и разбор ошибок.

Критерий приёмки: выполнение ПИ-01–ПИ-08, наличие обученной модели, воспроизводимых команд обучения и оценки, контрольного набора и полного комплекта поставки. Проверки должны завершаться на базовой среде из раздела 4.

## 13 Комплект поставки

В состав результата входят исходный код; requirements.txt с закреплёнными версиями; файл настроек; модель с метаданными; размеченные сеансы и реестр данных; генератор учебных PCAP; автоматические проверки; руководство пользователя; протокол приёмки и сравнительный отчёт о качестве методов.

Руководство должно содержать подготовку окружения, команды анализа, обучения и оценки, описание параметров, примеры результатов и перечень поддерживаемых входных данных. Протокол должен содержать версии Python и библиотек, сведения о базовой системе и результаты ПИ-01–ПИ-08.
